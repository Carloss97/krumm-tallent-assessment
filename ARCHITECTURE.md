# Project Architecture

Overview
-
This repository is a monorepo-style project containing a React frontend (Vite) and a Node.js/Express backend colocated in the same repository. The split is now explicit in code: frontend code lives in `src/`, backend code lives in `server/`, and the database layer is wrapped by `server/db.js` so it can switch implementations.

Frontend responsibilities
-
- UI composition and routing: `src/App.jsx`, `src/main.jsx`, `src/components/`, `src/games/`, `src/contexts/`, `src/hooks/`.
- Client-side telemetry and state: browser session state, consent, report rendering, game flow.
- Build/runtime: Vite output in `dist/`.

Frontend dependencies (current)
-
- `react`, `react-dom`, `react-router-dom`, `framer-motion`, `recharts`, `lucide-react`, `classnames`.

Backend responsibilities
-
- API routes and auth: `server/index.js`.
- Storage and persistence: `server/db.js` adapter, `server/db.sqlite.js` implementation, `server/db.pg.js` scaffold.
- Security and middleware: `helmet`, `cors`, `compression`, `rateLimiter`, token services.
- Observability: `prom-client`, request logging, health/readiness endpoints.

Backend dependencies (current)
-
- `express`, `cors`, `helmet`, `compression`, `dotenv`, `jsonwebtoken`, `pino`, `prom-client`, `uuid`, `@google/generative-ai`, `better-sqlite3`.

Storage note
-
- SQLite is still the active implementation by default. `server/db.js` now selects the client via `DB_CLIENT` or `DATABASE_URL`, and `server/db.pg.js` is the scaffold for a Postgres move.

High level layout
-
- Frontend: `src/` — React 19 + Vite build. Main entry: `src/main.jsx` and `src/App.jsx`.
- Backend: `server/` — Express app. Main entry: `server/index.js`.
- DB: `server/app.db` (SQLite file managed by `better-sqlite3`) and the DB adapter files in `server/`.
- Static build: `dist/` (generated by `vite build`). `server/index.js` will serve `dist/` if present.

API surface (summary of routes in `server/index.js`)
-
- Public / health:
  - `GET /health` — health check
  - `GET /ready` — readiness (DB, disk, Gemini key checks)
  - `GET /metrics` — Prometheus metrics
  - `GET /api/feature-flags` — runtime feature flags
  - `POST /api/telemetry` — lightweight telemetry collector (writes to disk)

- AI endpoints (rate-limited + circuit breaker):
  - `GET /api/ai/health` — checks Gemini connectivity
  - `POST /api/ai/generate` — request generation from Google Gemini

- Auth:
  - `POST /api/auth/participant` — participant authentication (upsert participant, return JWT)
  - `POST /api/auth/recruiter` — recruiter authentication (simple env-based credential)

- Participant session management (requires JWT):
  - `POST /api/session` — save session payload
  - `GET /api/session/:id` — get session by id
  - `GET /api/sessions` — list participant sessions
  - `GET /api/participant/:id` — participant profile

- Recruiter endpoints (require recruiter JWT):
  - `GET /api/recruiter/sessions` — list sessions (analytics)
  - `GET /api/recruiter/analytics` — recruiter analytics summary
  - `GET /api/recruiter/analytics/v2` — extended analytics with calibration snapshot

Data model (current SQLite tables)
-
- `sessions` — stores raw `payload` JSON plus `participant_id`, `participant_email` and timestamps.
- `participants` — participant metadata keyed by `participant_id`.
- `session_metrics` — lightweight normalized metrics per game linked to `sessions(id)`.

Runtime behaviors that affect deployment
-
- The backend writes telemetry and health probe files to disk (`.runtime/` and `server/app.db`). This is incompatible with many serverless environments (Cloudflare Pages Functions, Cloudflare Workers) which do not allow persistent filesystem storage.
- Uses `better-sqlite3` (native binary) which requires a Node.js environment with native module support and cannot run on Cloudflare Pages/Workers.
- `server/index.js` can serve the frontend build when `dist/` exists.

Recommended architecture (safe separation)
-
1. Frontend: deploy static assets to Cloudflare Pages (or any static host). Keep the `src/` app and `vite` build pipeline unchanged.
2. Backend: deploy the Express API to a Node-friendly host (Render, Fly, Railway, Cloud Run, or a VM). The backend requires native modules and writable disk for SQLite in current form.
3. Database: migrate from local SQLite to a managed DB (Postgres recommended: Neon or Supabase) so backend can scale and be hosted serverlessly or as a managed service.
4. If you prefer a single provider: deploy frontend to Pages and backend to a separate service; set CORS and environment variables accordingly.

Migration considerations (SQLite -> managed DB)
-
- Tables are small and straightforward (sessions, participants, session_metrics). Map `payload` JSON columns to `jsonb` (Postgres) to preserve raw payloads and use normalized `session_metrics` for queryable metrics.
- Replace `better-sqlite3` usage in `server/db.js` with a query library/driver (`pg`, `knex`, or an ORM) and update `saveSession`, `getSession`, `getAllSessions`, `upsertParticipant` functions.
- Ensure migration handles existing `server/app.db` export/import if you need to preserve historical data.

Notes on AI integration
-
- The backend uses `@google/generative-ai` to call Gemini — keep keys out of the repo and use environment variables. Circuit-breaker and rate-limiting are implemented server-side and should be retained.

Short checklist before changing hosting
-
- [ ] Decide where backend will run (Node host vs serverless). If serverless on Workers, plan DB/storage change.
- [ ] Choose managed database (Postgres recommended) and plan schema migration.
- [ ] Replace filesystem telemetry writes with object storage or logging service (S3/GCS/Cloudflare R2 / external logging).
- [ ] Update `server/db.js` to use chosen DB client and add connection config via env vars.
- [ ] Update CI / deploy docs (see DEPLOYMENT.md)

## 🔄 User Journey & Data Flow

### 1️⃣ **Authentication Flow**

```
User Input (participantId, email, accessCode)
    ↓
AuthPage → POST /api/auth/participant
    ↓
Server: validateParticipantCredentials()
    ↓
Server: upsertParticipant() → DB
    ↓
Server: generateParticipantToken() → JWT
    ↓
Response: { participantToken, expiresIn }
    ↓
Frontend: Store token in sessionStorage
    ↓
✅ Redirect to Intro (now authenticated)
```

### 2️⃣ **Game Assessment Flow**

```
User starts assessment
    ↓
Intro.jsx → dynamically loads GAME_FLOW (7 games)
    ↓
GameLayout wraps each game + TelemetryContext
    ↓
Game runs locally:
  - Records trial events (start, response, score, errors)
  - Captures cursor data (position, velocity, hesitation)
  - Captures webcam data (blinks, head pose, quality)
  - Validates consent (per-game check)
    ↓
User completes all 7 games
    ↓
sessionData accumulated in browser memory with:
  - game scores/errors/duration per game
  - trial-level telemetry (cursor, webcam, events)
  - consentState (which data user allowed)
    ↓
✅ All games complete → Proceed to Report
```

### 3️⃣ **Report Generation Flow**

```
Report.jsx receives sessionData
    ↓
1. TRY: Call Gemini AI
   POST /api/generateAIReport (future enhancement)
   → Generative AI fallback chain (1.5-flash → 2.0-flash → 2.5-lite)
   → Parse JSON response
   ✓ Success: Use AI report
   ✗ Fail: Fall back to heuristic
    ↓
2. Heuristic Fallback (always works):
   - normalizeGameScores() → 0-10 per game
   - calculateOverallScore() → weighted composite
   - generateHeuristicReport() → fill template
     - Identify top 3 strengths
     - Identify development areas
     - Match to career profiles
     - Set confidence score (55-80%)
     - Set recommendation tier
    ↓
3. UI Rendering:
   - Display scores heatmap
   - Show strengths panel
   - Show recommendations
   - Dev telemetry panel (if demo mode)
    ↓
4. User can:
   - Review report
   - Toggle demo telemetry view
   - Download report (future)
   - Save to database (if permitted)
```

### 4️⃣ **Data Persistence Flow (When Saving)**

```
User clicks "Save Assessment"
    ↓
Frontend: Show ConsentModal if not yet shown
    ↓
User grants consent: POST /api/session
  Headers: { Authorization: Bearer <JWT> }
  Body: {
    participant: { participantId, fullName, email },
    games: [...],
    report: { summary, strengths, recommendation, ... },
    telemetry: { cursor: [...], webcam: [...], events: [...] },
    consentState: { cursor: true, webcam: true, ... }
  }
    ↓
Server: authenticateToken() → Validate JWT
    ↓
Server: requireParticipant() → Check ownership
    ↓
Server: saveSession(payload) → DB transaction
    ↓
Database: INSERT INTO sessions (participant_id, data_json, created_at)
    ↓
Response: { sessionId, timestamp }
    ↓
✅ Frontend: Show "Saved! Session ID: 123"
```

## 🔐 Security Layers

### Token-Based Auth
```
1. POST /api/auth/participant
   → Server generates JWT token
   → Token stored in sessionStorage (browser)

2. All protected endpoints require:
   Authorization: Bearer <token>

3. Server validates:
   - Token signature
   - Token expiration (1 hour)
   - Participant ownership (user can only access own data)

4. Invalid/expired token:
   → 401 Unauthorized
   → Frontend: Clear token, redirect to login
```

### Data Isolation
```
- Participants can only read/write their own sessions
- No participant A can access participant B's data
- Email validation prevents duplicate/invalid accounts
- Database constraints enforce referential integrity
```

## 📊 Database Schema (SQLite)

### Participants Table
```sql
CREATE TABLE participants (
  participant_id TEXT PRIMARY KEY,
  full_name TEXT,
  email TEXT UNIQUE NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  last_authenticated TIMESTAMP
);
```

### Sessions Table
```sql
CREATE TABLE sessions (
  session_id INTEGER PRIMARY KEY AUTOINCREMENT,
  participant_id TEXT NOT NULL,
  data_json TEXT NOT NULL,        -- Full JSON (games, report, telemetry)
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (participant_id) REFERENCES participants(participant_id)
);
```

## 🚀 Deployment Considerations

### Frontend (Vite Build)
```
npm run build
  → dist/ folder
  → Deploy to: Vercel, Netlify, S3, or static hosting
  → Set VITE_API_BASE_URL to production backend URL
  → Keep .env (with real API_BASE_URL) secure
```

### Backend (Node.js)
```
Node server/index.js --env=production
  → Ensure PORT env var set
  → Create DB_PATH directory
  → Add HTTPS in reverse proxy (nginx, Caddy)
  → Add rate limiting middleware
  → Add proper CORS configuration
  → Use process manager (PM2, systemd)
```

### Database
```
SQLite file: assessments.db
  → Should be in persistent storage (not ephemeral)
  → Backup regularly
  → For scale: Migrate to PostgreSQL/MySQL
```
